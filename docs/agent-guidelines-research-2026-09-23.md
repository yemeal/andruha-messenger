# Основания для универсального AGENTS.md

Проверено 23 сентября 2026 года. Первичные источники открыты и прочитаны; продуктовые тесты не запускались.
Документ объясняет решения для шаблона, а не заменяет инструкции конкретного сервиса.
«Рекомендация» ниже — инженерный вывод для этих проектов; личные правила владельца явно отделены от требований источников.

## 1. Форма и область действия AGENTS.md

- OpenAI рекомендует короткие, конкретные инструкции: карта проекта, рабочие команды, ограничения, ожидания от PR и проверяемое определение готовности. Подробные процедуры можно вынести в связанные документы. [OpenAI: best practices][oa-practices]
- В инструкции полезно превращать повторяющуюся обратную связь и помещать её ближе к области применения. Общий учебник программирования быстро вытесняет важные проектные сведения. [OpenAI: customization][oa-custom]
- Codex собирает инструкции от корня проекта к рабочему каталогу; более близкие инструкции имеют приоритет. В каталоге выбирается максимум один файл: сначала `AGENTS.override.md`, затем `AGENTS.md`, затем настроенные fallback-имена. [OpenAI: AGENTS.md][oa-agents]
- Документация указывает общий предел загружаемых проектных инструкций `project_doc_max_bytes`, по умолчанию 32 KiB. Нельзя считать, что произвольно большой набор файлов будет прочитан полностью. [OpenAI: AGENTS.md][oa-agents]
- Рекомендация: единый компактный шаблон плюс адаптация команд, путей, публичных контрактов и исключений. Для самостоятельных Git-репозиториев сервисов базовые правила должны быть доступны внутри их checkout.

## 2. DDD, богатая модель и гексагональная архитектура

- Evans разделяет Entity с устойчивой идентичностью и Value Object без концептуальной идентичности; для VO рекомендует неизменяемость. Богатая модель выражает знания и поведение предметной области. [DDD Reference, разделы Entities / Value Objects][ddd]
- Aggregate задаёт границу согласованности: корень отвечает за общие инварианты; внешние объекты обращаются к корню. Границы агрегатов также направляют проектирование транзакций и распределения. [DDD Reference, Aggregates][ddd]
- Следствие для инструкции: проверять состояние объекта при создании/восстановлении, а допустимость перехода — в доменном поведении. Входной DTO и проверка в HTTP-обработчике не заменяют инварианты агрегата.
- Cockburn отделяет внутреннее приложение от внешних технологий через порты и адаптеры; приложение должно тестироваться без реального UI и БД. Число портов определяется значимыми взаимодействиями, а не формой шестиугольника. [Исходная статья][hex]
- Рекомендация: domain владеет бизнес-правилами; application организует сценарий и транзакционные границы; adapters переводят HTTP, SQL и сообщения. Не создавать интерфейс на каждый класс без реальной границы.
- Pydantic внутри domain — осознанный выбор владельца. Требование независимости от инфраструктуры здесь не означает запрет Pydantic или обязательное переписывание моделей на dataclasses.
- `DomainModel → Entity → MutableEntity → VersionedMutableEntity`, UTC, UUIDv7 и `_apply_changes` — соглашения проектов, не обязательные элементы DDD. Их точные гарантии надо проверить в коде сервиса.
- Fowler описывает строгий CQS, но сам допускает полезные исключения. Практическое правило: query не меняет наблюдаемое состояние; явно названная command может возвращать результат своего действия. [Fowler: CQS][cqs]
- Инженерный вывод: не разбивать атомарное действие с результатом на отдельные write/read ради буквального CQS — между вызовами может измениться состояние. Существующий `bool` результата мутации сам по себе не является нарушением архитектуры.

## 3. Pydantic v2: гарантии и ограничения

- `frozen=True` блокирует присваивание атрибутов, но не делает граф объектов глубоко неизменяемым: вложенный `dict` остаётся изменяемым. Рекомендация: защищать контейнеры и их элементы от внешней мутации. [Models: faux immutability][p-models]
- `@model_validator(mode="after")` выполняется после проверки модели, получает экземпляр и должен вернуть его. Подходит для межполевых инвариантов; проверка отдельного поля может оставаться в типе/`Field`/field validator. [Validators][p-validators]
- `validate_assignment` выключен по умолчанию и включает проверки при присваивании. Документация не обещает транзакцию нескольких присваиваний или автоматический откат всего агрегата. [Configuration][p-config]
- Рекомендация для «всегда валиден»: сначала проверить полное отделённое кандидатное состояние; затем применить доменные поля, время и версию согласованно. При отказе исходное состояние и события должны сохраниться. Это требование к реализации, не встроенная гарантия Pydantic.
- Использовать проверенный механизм сервиса, например `_apply_changes`; не вводить рядом второй. Доступ к собственному защищённому helper внутри модели допустим; внешний обход инвариантов через `object.__setattr__`, `__dict__` или reflection — нет.
- Базовый `BaseModel.model_copy(update=...)` **не валидирует обновления**; `deep=True` этого не меняет. Локальное переопределение метода может иметь другой контракт: сначала прочитать его реализацию. [BaseModel API][p-base]
- `model_construct()` создаёт модель без валидации. Нельзя использовать его как обычный путь создания/восстановления доменного состояния, если требуется гарантия инвариантов. [Models][p-models]
- `revalidate_instances` по умолчанию равен `"never"`; настройка не распространяется автоматически на вложенные типы. Повторная передача экземпляра в `model_validate` не доказывает полной повторной проверки его состояния. [Configuration][p-config]
- Значения по умолчанию обычно не валидируются: для требуемой проверки использовать существующую конфигурацию `validate_default=True` либо соответствующий параметр поля. [Fields][p-fields]
- `default`, `default_factory`, `alias` внутри `Annotated[..., Field(...)]` не учитываются статическими анализаторами при синтезе `__init__`; документация рекомендует форму присваивания. Сам `Annotated` подходит для ограничений и метаданных. [Fields: annotated pattern][p-fields]
- Требование владельца «default строго внутри `Field`» совместимо с рекомендацией документации:

```python
foo: Annotated[str | None, Field(description="...")] = Field(default=None)
```

Исходное `foo: Annotated[str | None, Field(default=None)]` допустимо во время исполнения, но требует оговорки о статической проверке. Существующие модели нельзя массово менять ради унификации без отдельной задачи.

## 4. TDD и pytest

- Kent Beck описывает список сценариев → один исполняемый тест → реализацию до прохождения нового и прежних тестов → при необходимости улучшение дизайна. Массовая предварительная запись всех тестов названа ошибкой. [Canon TDD][tdd]
- Локальный [skill `tdd`](C:/Users/Alex/.agents/skills/tdd/SKILL.md) требует заранее согласованных публичных границ тестирования и относит рефакторинг к стадии review после RED → GREEN. Это совместимо с отдельным ограниченным проходом улучшений после GREEN; не нужно приписывать эту локальную организацию Beck.
- Тесты должны наблюдать поведение через согласованный публичный интерфейс. Ожидаемые значения берутся из спецификации или независимо разобранного примера, а не повторяют реализацию. Это правило выбранного владельцем skill `tdd`.
- pytest поддерживает несколько расположений тестов; для новых проектов рекомендует `src` layout и `importlib`. Это не основание самовольно менять рабочую структуру существующего сервиса. [Good practices][pytest-layout]
- Рекомендация владельцу: пути тестов отражают уровень и область: `tests/unit/domain/...`, `tests/unit/application/...`, `tests/integration/<adapter>/...`, отдельные `tests/e2e/...` при наличии таких сценариев. Точные каталоги адаптируются к реальному репозиторию.
- Общие fixtures размещать в ближайшем подходящем `conftest.py`; scope выбирать по изоляции состояния. Небольшая fixture с одним изменением состояния и связанным cleanup упрощает безопасный teardown. [Fixtures][pytest-fixtures]
- Собственные markers регистрировать; строгая проверка неизвестных markers помогает ловить опечатки. Использовать существующую конфигурацию и зависимости сервиса. [Markers][pytest-markers]
- Личные правила владельца, подтверждённые в этой задаче: ожидаемый RED нового согласованного теста — сообщить и продолжить реализацию по плану, тест не менять. Неожиданное падение — сообщить и остановить исправления до одобрения.
- Любые изменения уже написанного теста требуют одобрения владельца. Не ослаблять assertions, не добавлять `skip`/`xfail`, не удалять тест ради GREEN. Технические примеры из [skill `pytest-skill`](C:/Users/Alex/.agents/skills/pytest-skill/SKILL.md) не отменяют этот запрет.
- Отчёт различает passed, failed, skipped и not run, отдельно unit/integration/e2e. Проверка сбора тестов и health endpoint не доказывают работу пользовательского сценария; это критерий честной верификации проекта.

## 5. Git и практическая читаемость

- Conventional Commits задаёт `<type>[scope][!]: description`; `feat` обозначает новую возможность, `fix` — исправление, несовместимость отмечается `!` или `BREAKING CHANGE`. Другие типы разрешены; обязательный полный набор префиксов стандарт не задаёт. [Спецификация 1.0.0][cc]
- Если изменение содержит разные типы работ, спецификация рекомендует по возможности несколько коммитов. Говорящие ветки, атомарность по ответственности, последовательность и merge через PR — дополнительные правила владельца. [FAQ][cc]
- Рекомендация: выразить Clean Code / KISS / YAGNI / DRY / SOLID проверяемыми действиями: ясные имена, одна связная ответственность, один уровень абстракции, бизнес-правило в одном месте, узкие контракты, совместимые реализации.
- Не превращать OCP в требование наследования, DRY — в объединение случайно похожего кода, а «маленькие функции» — в произвольный предел строк. Обобщение и паттерн должны решать текущую задачу.
- Комментарии объясняют бизнес-причину, компромисс или внешнее ограничение. Небольшая уборка допустима в границах задачи после GREEN; она не разрешает менять публичный контракт, чужие правки или тесты без требуемого согласования.

## 6. Десять ловушек слишком жёстких формулировок

| Ловушка | Уточнение для инструкции |
| --- | --- |
| «Frozen означает полную неизменяемость» | Проверять вложенные контейнеры и aliasing. |
| «`model_copy` проверит изменения» | У базового Pydantic проверки нет; читать локальное переопределение. |
| «Assignment validation обеспечит атомарность» | Проверять полный кандидат до применения изменений. |
| «Любой `model_validate` повторно проверяет всё» | Учитывать `revalidate_instances` и вложенные модели. |
| «Default внутри Annotated прозрачен для typing» | Default внутри `Field` в форме присваивания сохраняет статическую сигнатуру. |
| «DDD запрещает Pydantic» | Это разрешённый выбор проекта; проверять поведение и зависимости. |
| «Команда никогда ничего не возвращает» | Допускать явный результат действия без скрытой записи в query. |
| «Любое падение требует исправить тест» | Ожидаемый RED и неожиданный сбой имеют разные правила; тест защищён approval. |
| «Все проверки всегда должны быть зелёными» | Фиксировать реальные результаты и blockers; не скрывать RED, skips или неисполненные проверки. |
| «Один большой AGENTS подходит всем» | Короткое общее ядро; проверенные команды и границы каждого сервиса. |

## 7. Что проверять при адаптации

1. Фактические Git root, инструкции, dirty state, стек, версии и команды из конфигурации/CI.
2. Реальные base models, фабрики, clock, идентификаторы, mutation helper, OCC и доменные ошибки.
3. Доступные публичные границы тестирования, fixtures, markers и намеренно незавершённые сценарии.
4. Публичные API, события и схемы; исключения, которые нельзя менять под видом общего улучшения.
5. Разделить обязательные правила владельца, подтверждённую реализацию и ещё не реализованные ожидания. Шаблон не является доказательством соответствия кода.
