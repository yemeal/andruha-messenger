## Стенд

Отдельный Compose project, собственная сеть и новые volumes:

- API Gateway → Identity API / User Profile API;
- отдельные PostgreSQL `17.10-bookworm` для Identity и Profile;
- Valkey `8.1.9-alpine3.24`, отдельные логические БД/пространства ключей;
- Kafka `3.9.2`, реальный topic `identity.events.v1`;
- процессы Identity relay и registration reconciler; в одном сценарии — два reconciler;
- собственные временные RSA/AES-ключи и сервисный токен.

Profile provisioning проходил через технический HTTP-прокси к настоящему Profile. Прокси позволял задержать ответ после реального commit и подменить сервисный токен. Он не создавал профили и не подменял БД.

Обе Alembic-миграции применены в контейнерах. Подключения, доверенные JWT-ключи,
сервисная аутентификация и адреса зависимостей заданы явно в сгенерированной
конфигурации. Отдельно корневой Compose прошел build, запуск всех process roles и
smoke `register → login → profile/settings/public profile`.

Для ограниченного времени тестов уменьшены интервалы polling/backoff и lease. Обычный стенд использовал лимит 50 попыток; отдельный сценарий проверял исчерпание лимита в 2 попытки. В эксплуатационных настройках интервалы и лимиты отличаются.

Множества user_id совпали во всех бизнес-таблицах и Outbox. Временные метки регистрации совпали. В завершённых регистрационных операциях password_hash очищен. Каждая активная сессия имеет ровно один неиспользованный refresh-токен. Сохранённые результаты refresh не содержат открытых токенов.

Kafka прочитан отдельным consumer с начала topic. Сверены event_id, key и весь
payload с Outbox. **34 доставки при 33 событиях — ожидаемый повтор:** relay был
остановлен после подтверждения Kafka, когда UPDATE статуса SUCCESS ещё
блокировался тестовым PostgreSQL trigger. После восстановления повторно
отправлены тот же event_id и payload; в Outbox осталась одна запись. Поэтому
потребителям требуется дедупликация по event_id. Exactly-once delivery не заявляется.

Проверка подтверждает сходимость после восстановления зависимостей. Во время аварии между commit Profile и финализацией Identity профиль временно существовал без пользователя; операция оставалась durable и позднее завершилась. Это saga, а не распределённая транзакция.

## Исправление Identity

В [RegisterUserHandler](../services/identity-service/src/app/application/use_cases/register/handler.py)
второй одинаковый запрос мог прочитать отсутствие операции, начать Argon2 и
затем увидеть уже созданного первым запросом пользователя. Ранний
UserAlreadyExistsError возвращал 409 для корректного повтора с тем же ключом.

Теперь этот путь повторно загружает регистрационную операцию по ключу. Одинаковый запрос получает сохранённый результат, другой ключ по-прежнему конфликтует. Добавлен детерминированный unit-тест; гонка повторно проверена восемью HTTP-запросами на Docker-стенде.

После исправления: **371 unit + 110 integration tests passed**. Ruff, форматирование, ty и git diff --check прошли. E2E-скрипты дополнительно проверены Ruff на ошибки синтаксиса и неиспользуемые имена. Полный автоматический wrapper `run.py` отдельно от ручного запуска тех же этапов целиком не прогонялся; его CLI и импорт проверены.

## Закрытые дефекты Gateway

### 1. Нет маршрута settings

Первичный прогон: `GET /api/v1/settings/me` через Gateway → **404**. В
[nginx.conf](../services/api-gateway/nginx.conf) добавлен маршрут
`/api/v1/settings/`; повторная приемка получила **200**.

Исправление: направить этот prefix в `user_profile_service` с общими proxy-настройками. Приёмка: GET/PATCH settings через Gateway, авторизация, ETag и replay.

### 2. Пустой Bearer закрывает анонимный публичный профиль

Первичный прогон: `GET /api/v1/profiles/{id}` без cookie через Gateway → **401**.
[proxy-common.conf](../services/api-gateway/proxy-common.conf) теперь удаляет
Authorization при отсутствии cookie и продолжает перезаписывать клиентский
заголовок. Повторная приемка получила **200**.

Исправление: формировать Authorization через `map`; при отсутствии cookie удалять заголовок. Клиентский Authorization по-прежнему должен перезаписываться. Приёмка: публичное чтение без cookie, защищённые routes → 401, подмена Authorization не принимается.

### 3. Поиск профиля попадает в цикл редиректов

`GET /api/v1/profiles?username=...` через Gateway → **301** на вариант с завершающим `/`; запрос `/api/v1/profiles/` → **307** обратно к маршруту Profile без `/`. Напрямую поиск возвращает **200**.

Причина была в отсутствии exact location `/api/v1/profiles`. После добавления
маршрута поиск возвращает **200** с сохранением query parameters без redirect-loop.

Все три изменения находятся в API Gateway PR #3; E2E не использует skip/xfail и
подтвердил каждый контракт отдельным сценарием.
